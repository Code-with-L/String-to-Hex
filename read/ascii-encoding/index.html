ASCII and Character Encoding

From seven bits to Unicode, and why "a character" is not a fixed number of bytes.

ASCII is a 7-bit character encoding assigning codes 0–127 to control characters, space, and printable English.

Seven bits was chosen so that a 7-bit code would also carry a parity bit in an 8-bit byte, which mattered when teleprinters were the reference. 128 characters was a deliberate economy.

Position is what gives the number meaning

’A’ = 65 = 4·16¹ + 1·16⁰ = 41₁₆ Four sixteen-times, plus one. The decimal code is the same quantity written differently.

The variable-width problem

ASCII cannot represent "é", "€" or "中". A single-byte extended encoding such as Windows-1252 can add 128 more characters but only those 128, and which 128 differs per alphabet. That is why legacy encodings are so confusing.

Unicode solves the coverage problem by assigning a code point to every character in every script. UTF-8 then encodes those code points in one to four bytes, chosen so that ASCII characters still cost exactly one byte.

Note JavaScript strings are sequences of UTF-16 code units, not bytes. A character outside the Basic Multilingual Plane — every emoji, for instance — occupies two of them. Encoding such a string to bytes therefore produces four bytes, not two. This is the single most common source of confusion when converting text to hex.

Which encoding should you use

  • UTF-8 for anything on the web, in files, or in a database — it is the only sane default today.
  • UTF-16 only when a system or protocol mandates it, such as the Windows registry or Java’s char streams.
  • A legacy code page only when reading historical data that is known to be in that encoding.
